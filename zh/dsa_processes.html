    数据共享协议流程

    本页是关于数据共享协议（DSA）的实施指导。它描述在两个组织之间执行 DSA 的技术流程，仅涵盖信任网络相关流程。其他流程计划在其他指南中介绍（参见其他流程在哪里）。

    草稿。本页位于 litlfred 复刻（fork）中，并非 WHO 指导文件。流程列表（P1 至 P15）是我们自己的结构；没有任何标准定义“DSA 流程”。标为“未经核实”的条目未对照源规范进行检查。

    要点

    • 无论 DSA 是否可计算，都需要相同的技术流程。密钥仍需注册。访问仍需决定、记录和撤销。
    • “可计算”只改变一件事：访问规则从何而来。
      • 可计算 DSA：从法律文本导出的 ODRL 2.2 Agreement。由程序在每次请求时对其进行评估。
      • 仅文档的 DSA：一份已签署的 PDF。由人阅读并手动配置系统。
    • GDHCN 是一种可能的信任锚，但不是唯一的。DSA 可以改为指定国家 PKI、某一方自己的 did:web 或本地列表。本页的任何内容都不要求使用 GDHCN。

    角色

    这些是角色，而非组织。一个组织可以担任多个角色。

    角色 对应
    数据提供方 ODRL assigner（ODRL 2.2 §2.1.3、§2.3）
    数据接收方 ODRL assignee（ODRL 2.2 §2.1.3）
    信任锚 信任网络锚；或 X.509 根 CA（RFC 5280 §6）
    持有密钥的一方 信任网络参与方、签发方
    验证方 Receiver；任何检查某一方签名或 TLS 证书的系统

    “数据提供方”和“数据接收方”是我们自己的用语。本指南中没有任何参与者使用这些名称。

    信任锚的选择

    DSA（或执行它的系统的策略）会说明其接受哪些锚。所接受的列表要么是一个 DID 文档，要么是一组 X.509 根。无需新的格式。

    锚 是什么 标准 加入所需的书面手续
    GDHCN WHO 的信任列表，以 did:web DID 文档形式发布，并由信任网络网关提供数据 DID Core 1.0、did:web、JsonWebSignature2020 证明（DID Trustlist v2） 入网流程
    国家 PKI 某个国家的 X.509 根 CA RFC 5280 路径验证（§6）和 CRL（§5） 国家规定
    自有 did:web 由某个部委或研究机构发布其自己的 DID 文档 DID Core 1.0、did:web 无。信任来自域名及其 TLS 证书
    本地列表 部署系统自己的已接受密钥或根的列表 DID 文档，或经 RFC 5280 检查的 PEM 根 由系统所有者自行决定

    另有两种选项，此处不推荐：

    • UDAP（HL7 FAST UDAP Security，STU）：试用标准。使用前需获得批准。
    • OpenID Federation：尚非最终规范。不予采用。

    RFC 5914（信任锚格式）仅以 ASN.1 表述“此根受信任”，没有 JSON 形式。因此，X.509 根的本地列表以 PEM 文件加 RFC 5280 检查的方式保存。

    P3. 向信任锚注册各方及其密钥

    • 角色。各方；信任锚运营方。
    • 触发条件。某一方将签署供他人验证的内容（令牌、凭证、QR 码），或将通过双向 TLS 进行连接。
    • 步骤。
      1. 选择 DSA 接受的一个或多个锚（见上文）。双方在协议中记录该选择。
      2. 办理该锚所要求的书面手续。
        • GDHCN：申请函、《参与条款》、技术评估、验收测试、上线（入网流程）。
        • 国家 PKI：按国家规定。
        • 自有 did:web 或本地列表：无。
      3. 为每种所需用途生成密钥。
        • GDHCN：KeyUsage 值集中的用途（例如 SCA、DSC、UP、TLS）。参见证书治理。
        • 其他锚：证书或验证方法所允许的密钥用途。
      4. 发布公钥。
        • GDHCN：通过信任网络网关发布密钥。
        • did:web：在该方的 DID 文档中添加一个 verificationMethod 条目（DID Core 1.0 §5.2，章节号未经核实）。
        • X.509：由 CA 签发证书。
        • 本地列表：将密钥或根交给另一方。
      5. 验证方获取该列表并检查其签名。
        • GDHCN：检索验证密钥 - DID。信任列表的证明为 JsonWebSignature2020（验证信任列表文档）。
        • X.509：按 RFC 5280 进行到所接受根的路径验证。
        • did:web：通过 HTTPS 解析 DID 文档。
    • 输入。密钥对；对于 GDHCN，还有申请函。
    • 输出。一个 DID 文档条目，或一份 X.509 证书；对于 GDHCN，为一个已签名的信任列表条目。
    • 标准。DID Core 1.0（W3C 推荐标准）。did:web 和 JsonWebSignature2020（非最终版；所有者已批准用于本项工作）。RFC 5280。IHE VHL 事务“Submit PKI Material with DID”（ITI-YY1）和“Retrieve Trust List with DID”（ITI-YY2）描述了相同的步骤（投票阶段；事务名称在本次会话中未经核实）。
    • 可计算？部分可以。步骤 2 由人完成。步骤 4 和 5 由程序完成。
    • 仅文档的 DSA。完全相同。只要有任何系统进行签名或通过双向 TLS 连接，仅有 PDF 的 DSA 仍然需要密钥。
    如果锚是 GDHCN

    本说明仅适用于各方选择 GDHCN 的情况。

    • GDHCN 按信任域对密钥分组，例如 DDCC、ICVP、IPS-PILGRIMAGE 和 PH4H。它没有用于 DSA 的信任域。
    • 使用来自另一个域的密钥签署 DSA 材料在技术上可行，但超出了该密钥规定的用途。
    • DSA 信任域将由 WHO 决定。本指南不提议设立此类信任域。
    • 加入 GDHCN 本身由文件管辖（《参与条款》、《行政与运营框架》）。它是一个在仅文档协议之上叠加技术流程的实际例子。参见概念。

    P15. 争议和违约处理

    • 角色。双方；监管机构；法律文本所指定的法院或仲裁方。
    • 触发条件。疑似违约：数据被用于超出目的的用途、未履行义务、泄露。
    • 步骤。
      1. 控制。暂停授权、客户端和密钥（P13，smart-trust-phw 流程 H）。
        • GDHCN 密钥：从信任列表中删除该 DSC（参见入网核对清单中的“DSC 生成与删除”）。
        • X.509 证书：撤销证书并发布 CRL（RFC 5280 §5）。出于隐私考虑，本指南建议使用 CRL 而非 OCSP（证书治理）。
        • did:web 密钥：从 DID 文档中删除 verificationMethod。
      2. 收集证据。审计记录（P12，smart-trust-phw 流程 G）、日志的哈希链（如有），以及双方签署的协议版本的哈希值（P2）。
      3. 遵循法律文本中的争议条款。
      4. 解决。恢复（解除暂停）、修订（P14）或终止（P14，然后通过 P13 撤销）。
      5. 通知法律要求通知的各方，例如数据保护机构。这取决于国家法律，不在本指南范围之内。
    • 标准。流程本身没有标准。在可计算 DSA 中，ODRL 2.2 的 consequence（§2.6.6）和 remedy（§2.6.7）可以说明义务未履行时的后果。争议本身属于法律事项。
    • 可计算？否：由人作决定。证据由程序生成。这是可计算 DSA 在此处带来的主要价值。
    • 仅文档的 DSA。相同。证据为日志加哈希值。

    当协议仅为一份已签署的 PDF 时

    一个实例。其中的名称均为虚构。部委 M 依据一份已签署的 PDF 与研究机构 I 共享一个数据集。不使用 ODRL。

    步骤 发生的事情 流程 由程序完成
    1 M 和 I 协商并签署一份 PDF。含安全控制措施的附件保持不公开 P1 无
    2 M 在一个不可变的 URL（例如 /dsa/42/v3）上发布该 PDF，连同其 SHA-256，以及一条带校验和的 DCAT 3 记录（§6.8.20）。如该 PDF 属机密，M 仅发布哈希值 P2 哈希值、目录
    3 I 的服务器证书由国家 PKI 签发，或由 I 发布一个 did:web P3 密钥发布
    4 M 的管理员手动注册 I 的客户端：客户端 id、双向 TLS 证书，以及与 PDF 相符的作用域。管理员的变更记录引用该 PDF 的 URL 和哈希值 P4 注册
    5 I 的服务器通过双向 TLS（RFC 8705）以客户端凭据方式获取令牌并调用 API P5 全部传输
    6 需要同意时，同意书为纸质表格，扫描后存入 FHIR Consent.source[x]，并将 Consent.policy.uri 设为该 PDF 的 URL（FHIR R4 Consent） P9 存储、查找
    7 M 的服务器根据其配置允许或拒绝每次调用 P11 检查（规则由人手动设定）
    8 每次调用都连同 PDF 的 URL 和哈希值一起记录。由人对照 PDF 的条款审阅日志。结束时，I 发送一封已签名的删除函；M 将其连同哈希值一并保存 P12 记录
    9 如 I 违反该 PDF，M 的管理员停用该客户端并撤销证书 P13、P15 机制
    10 到期时触发提醒。管理员停用该客户端。I 返还或删除数据 P14 机制

    此处由人手动完成、而可计算 DSA 会自动检查的事项：将条款转化为作用域（步骤 4）；检查每个请求的目的（仅当客户端说明目的时才可能）；到期（步骤 10）；义务检查（步骤 8）。

    两类 DSA 中相同的部分：密钥、传输、令牌、日志和撤销。正因如此，这些流程值得为每个 DSA 记录在案。

    此处展示 FHIR R4 Consent，是因为 IHE PCF 使用它。本指南采用 FHIR R4 4.0.1，与 smart-base 和 smart-trust-phw 相同（所有者，2026-11-07），因此 Consent 采用本指南自身的版本。smart-trust-phw 的 Consent 页面描述了明示同意和默示同意。
